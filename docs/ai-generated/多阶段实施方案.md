## 1. 当前代码基线

截至本文编制时，仓库中尚无前端、后端、数据库迁移、容器和 CI 代码。现有有效内容为：

- 原始笔试题及其附件。
- `docs/ai-generated/技术方案.md`。
- `docs/ai-generated/README.md`。
- 基础 `.gitignore`。

因此，本计划从工程初始化开始。不能把技术方案中描述的功能视为已经实现，也不能在阶段验收中用文档代替源码和运行结果。

## 2. 分阶段原则

1. 每阶段只处理已列入范围的内容，不顺手扩展下一阶段功能。
2. 每阶段开始前读取上游方案和当前代码，结束后运行本阶段要求的检查。
3. 每阶段必须留下可复核的源码、测试或运行证据，不能只完成目录占位。
4. 先完成后端业务闭环，再完善前端异步体验；但每个业务能力尽量形成纵向可验证切片。
5. 数据库字段、枚举和接口字段以技术方案为基线；若实现中调整，先同步设计文档并说明原因。
6. 不引入真实 AI、视频、Redis、消息队列、WebSocket、模板后台或完整账号系统。
7. 每阶段建议单独提交，提交信息表达阶段结果，便于回滚和审查。

## 4. 阶段 0：方案冻结与环境预检

### 4.1 目标

把“可自行选择”的内容固定下来，避免开发中反复更换版本、包管理器、端口和目录结构。

### 4.2 工作内容

- 检查本机及容器环境：Git、Docker、Docker Compose、Node.js、npm、JDK、Maven。
- 固定具体版本并记录到根 README 草稿：Java 17、MySQL 8.x，以及实际采用的 Next.js、Spring Boot、MyBatis 补丁版本。
- 固定项目目录：

```text
frontend/
backend/
docs/ai-generated/
.github/workflows/
docker-compose.yml
.env.example
README.md
```

- 固定开发端口：前端 `3000`、后端 `8080`、本地 MySQL `3306`；后续引入 Compose 时再决定是否使用不同的宿主机映射端口。
- 固定前端样式方案，建议 Tailwind CSS；固定包管理器为 npm，并提交 `package-lock.json`。
- 固定后端构建为 Maven Wrapper。
- 明确环境变量命名：数据库连接、JWT 密钥、上传目录和模拟配置。

### 4.3 交付物

- 根 README 的环境和结构草稿。
- `.env.example` 的配置键清单，不含真实密钥。
- 如技术选型发生变化，同步更新技术方案。

### 4.4 通过标准

- 所有必要工具版本可查询。
- 端口未被现有进程冲突占用，或已经调整方案。
- 版本、目录、端口和命令不再存在“待定”项。

### 4.5 本阶段不做

- 不实现业务接口、页面和数据表。
- 不下载或引入不必要的 UI/基础设施组件。

## 5. 阶段 1：工程骨架与基础设施

### 5.1 目标

建立前端、后端和数据库都能启动的最小工程，并形成后续开发的固定入口。

### 5.2 后端工作

- 创建 Spring Boot Maven 工程。
- 引入 Web、Validation、Security、MyBatis、MySQL Driver、Flyway、JWT、Actuator 和 Test 依赖。
- 建立推荐包结构：

```text
controller/
application/
domain/
infrastructure/
config/
common/
```

- 提供 `application.yml` 和环境变量覆盖方式。
- 暴露不含敏感信息的 `/actuator/health`。
- 加入 Maven Wrapper。

### 5.3 前端工作

- 创建 Next.js App Router + TypeScript 工程。
- 配置 lint、TypeScript、test 和 build 脚本。
- 建立 `app/`、`components/`、`lib/api/`、`types/`、`tests/` 等目录。
- 设置统一的 API 基础地址读取方式。
- 提供最小首页占位和全局布局，但不提前制作业务页面。

### 5.4 容器工作

- 提供 MySQL 服务和命名数据卷。
- 为前后端准备 Dockerfile 骨架。
- 本阶段允许 Compose 只保证基础服务启动；最终健康检查和生产式构建在阶段 10 完成。

### 5.5 测试与验证

```text
frontend: npm run lint, npm run type-check, npm test, npm run build
backend:  ./mvnw test, ./mvnw package
```

- 启动后端，确认健康检查通过。
- 启动前端，确认首页可访问。
- 后端能够连接 MySQL。

### 5.6 通过标准

- 新环境根据 README 草稿可以完成依赖安装和构建。
- 前端、后端、MySQL 均能独立启动。
- 仓库没有提交依赖目录、构建产物、数据库数据或真实密钥。

### 5.7 本阶段不做

- 不实现登录、模板、上传和任务业务。

## 6. 阶段 2：数据库与后端公共基础

### 6.1 目标

落实数据库结构和后端统一协议，为后续所有业务提供稳定基础。

### 6.2 数据库工作

使用 Flyway 创建：

```text
app_user
template_category
material_template
asset
production_task
production_task_asset
```

- 严格落实技术方案中的主键、唯一键、普通索引、外键和检查约束。
- 创建分类、至少三个模板、至少两个用户的种子数据。
- 用户密码使用 BCrypt 哈希。
- 模板覆盖至少 1 张、2 张和 3 张图片要求，以及至少两个分类。
- 加入公开的本地模板封面和模拟结果图；记录素材来源。

### 6.3 后端公共能力

- 建立领域枚举和实体。
- 建立 MyBatis Mapper 及基础查询。
- 建立 `ApiResponse<T>`、列表响应、错误响应和字段错误模型。
- 建立业务异常层次和全局异常处理器。
- 建立 `requestId` 过滤器或拦截器，并写入日志上下文和响应。
- 建立统一时间序列化规则。

### 6.4 测试与验证

- Flyway 在空数据库可一次性迁移成功。
- 重启应用不会重复插入冲突种子数据。
- 使用数据库元数据或集成测试验证核心索引和唯一约束。
- 验证统一异常响应不包含堆栈、SQL 和物理路径。

### 6.5 通过标准

- 六张表及种子数据真实存在。
- 后端能够通过 MyBatis 查询预置用户、分类和模板。
- 数据库结构与技术方案一致；若不一致，已有明确变更记录。

### 6.6 本阶段不做

- 不开放业务 Controller。
- 不实现模板管理 CRUD。

## 7. 阶段 3：登录认证闭环

### 7.1 目标

用户能够通过数据库预置账号登录，业务接口能够可靠取得当前用户身份。

### 7.2 后端工作

- 实现 `POST /api/v1/auth/login`。
- 使用 BCrypt 校验密码，不使用 MD5 或明文密码。
- 生成包含用户 ID、用户名和过期时间的 JWT。
- 实现 `GET /api/v1/auth/me`。
- 实现 `POST /api/v1/auth/logout` 的无状态退出响应。
- 配置 Spring Security：登录、模板公开；其他业务接口默认需要认证。
- 区分无令牌、无效令牌、令牌过期和禁用用户。
- 日志不得输出密码或完整 JWT。

### 7.3 前端工作

- 实现 `/login` 页面。
- 实现认证 API 客户端和令牌携带。
- 实现当前用户状态恢复。
- 未登录访问业务页跳转到登录页。
- 令牌失效时清除用户级缓存并回到登录页。
- 提供退出登录入口；退出时停止未来的任务轮询能力。

### 7.4 测试

后端：正确密码、错误密码、未知用户、禁用用户、过期/篡改 JWT、受保护接口。

前端：登录中按钮禁用、错误提示、成功跳转、刷新恢复用户、令牌失效跳转。

### 7.5 通过标准

- 两个预置用户均可登录。
- 错误用户名和密码统一返回 `INVALID_CREDENTIALS`。
- 未认证无法访问受保护测试接口。
- 刷新页面后可通过 `/auth/me` 恢复身份。

### 7.6 本阶段不做

- 不做注册、找回密码、刷新令牌、服务端撤销列表和角色管理。

## 8. 阶段 4：模板浏览闭环

### 8.1 目标

用户登录后能够从 Java 后端获取、筛选和查看模板。

### 8.2 后端工作

- 实现 `GET /api/v1/templates`，返回分类与模板卡片。
- 实现 `GET /api/v1/templates/{templateId}`。
- 只返回启用分类和模板。
- 分类不存在返回空列表，模板不存在返回 `TEMPLATE_NOT_FOUND`。
- 公开提供模板封面和模拟结果静态资源。

### 8.3 前端工作

- 实现模板列表页 `/`。
- 实现分类切换，不在前端写死模板数据。
- 实现模板详情页 `/templates/[templateId]`。
- 展示图片数量、类型和大小要求。
- 完成加载、空数据、失败重试和模板不存在状态。
- 保留登录用户和“我的制作”导航入口。

### 8.4 测试

- 后端测试启用过滤、分类过滤、排序和不存在模板。
- 前端测试分类切换、接口失败、空列表和详情 404。

### 8.5 通过标准

- 数据库修改模板数据后，页面无需改代码即可反映变化。
- 至少三个模板能展示不同分类和不同图片数量要求。
- 桌面端布局清晰，小屏可完成浏览和进入详情。

### 8.6 本阶段不做

- 不做模板新增、编辑和删除。
- 详情页暂不真正上传图片。

## 9. 阶段 5：图片上传闭环

### 9.1 目标

用户能够按模板要求上传真实图片，文件保存在服务端，素材元数据进入数据库。

### 9.2 后端工作

- 实现 `POST /api/v1/assets`。
- 实现 `GET /api/v1/assets/{assetId}/content`。
- 从认证上下文取得用户，不接受客户端指定归属用户。
- 校验模板存在、文件非空、文件大小和真实类型。
- 使用 UUID 存储名，防止路径穿越和同名覆盖。
- 文件成功落盘后写入 `asset`；数据库失败时补偿删除文件。
- 素材内容接口校验用户归属，跨用户访问返回 404。
- 配置容器数据卷和上传目录。

### 9.3 前端工作

- 根据 `requiredImageCount` 动态生成上传位。
- 每个上传位独立管理 `EMPTY/UPLOADING/SUCCESS/FAILED`。
- 支持选择、即时预览、替换、移除、上传失败和重试。
- 前端先校验类型和大小，但后端错误仍需正确展示。
- 页面卸载或替换文件时释放 `blob:` 预览 URL。
- 所有上传位成功前，不允许进入创建任务动作。

### 9.4 测试

后端：合法 JPG/PNG、空文件、超限文件、伪造类型、模板不存在、跨用户读取、存储失败补偿。

前端：多个上传位互不影响、失败重试、替换/移除、未完成时按钮禁用。

### 9.5 通过标准

- 上传成功后，文件真实存在于服务端/数据卷，数据库存在对应元数据。
- 刷新详情页后旧的本地预览可以消失，但已创建的服务端素材不会依赖浏览器临时地址。
- 用户 A 无法读取用户 B 的素材。

### 9.6 本阶段不做

- 不做对象存储、裁剪、压缩、图片编辑和素材管理页。

## 10. 阶段 6：任务受理与查询闭环

### 10.1 目标

建立任务数据闭环，但暂不执行三个后台阶段，以便独立验证受理、关联和查询规则。

### 10.2 后端工作

- 实现 `POST /api/v1/tasks`。
- 校验模板、素材数量、重复素材、素材归属、状态、类型、大小和物理文件。
- 事务内写入 `production_task` 和有序 `production_task_asset`。
- 实现 `GET /api/v1/tasks` 和 `GET /api/v1/tasks/{taskId}`。
- 查询条件始终包含当前用户 ID。
- 定义任务 DTO、失败 DTO 和状态/阶段映射。
- 本阶段允许通过测试配置禁用执行器，使任务稳定停留在 `QUEUED`，用于验证受理逻辑；该配置不得成为正式默认行为。

### 10.3 前端工作

- 模板详情页加入创建任务动作。
- 提交期间禁用按钮，避免用户连续点击。
- 创建成功后跳转 `/tasks` 并带出任务 ID 或触发任务列表失效刷新。
- 创建失败保留已上传素材，允许用户修正或重试。

### 10.4 测试

- 任务和素材关联在同一事务中成功或失败。
- 素材数量错误、重复 ID、缺失素材、跨用户素材和文件丢失均不能创建有效任务。
- 用户只能查询自己的列表和详情。
- 查询接口不修改任务状态。

### 10.5 通过标准

- 合法请求快速返回 `taskId` 和 `QUEUED`。
- 数据库记录的素材顺序与请求数组一致。
- 页面不会在创建接口返回后继续显示“正在提交”。

### 10.6 本阶段不做

- 不实现后台阶段推进和轮询优化。
- 不实现严格幂等键。

## 11. 阶段 7：三阶段异步执行

### 11.1 目标

完成题目最核心的 Java 后台异步处理和可控失败。

### 11.2 工作内容

- 配置 Spring `ThreadPoolTaskExecutor` 有界线程池。
- 创建任务事务提交后提交 `taskId`，不把未提交事务中的实体直接传入异步线程。
- 实现独立阶段处理器：

```text
MaterialCheckStep
SimulatedGenerationStep
ResultFinalizationStep
```

- 执行器按固定顺序调用三个处理器。
- 每步开始前持久化当前阶段。
- 支持三个阶段独立耗时配置和指定阶段失败。
- 失败后保存失败编码、阶段、原因和完成时间，并停止后续步骤。
- 成功后保存结果地址和完成时间。
- 使用条件更新或乐观锁，终态不能被旧更新覆盖。
- 捕获线程池拒绝：将已经创建的任务标记为 `FAILED`，`stage = null`，错误编码为 `TASK_QUEUE_FULL`；接口返回 `503` 及 `taskId`。
- 记录带 `taskId` 的结构化日志。

### 11.3 关键事务边界

- 创建任务事务只负责创建记录和关联。
- 每次状态/阶段更新使用独立的短事务，确保前端能够观察中间阶段。
- 不能使用一个覆盖全部耗时步骤的大事务，否则中间状态不可见且长期占用数据库连接。

### 11.4 测试

- 正常顺序严格为 `MATERIAL_CHECK → GENERATING → FINALIZING`。
- 分别在三个阶段失败，验证后续阶段未调用。
- 查询接口不会推动任务。
- 成功/失败终态不会回退。
- 队列拒绝后不存在永久 `QUEUED` 记录。
- HTTP 创建接口耗时明显小于三阶段总模拟耗时。

### 11.5 通过标准

- 页面关闭不影响已经受理的任务继续执行。
- 数据库和查询接口能够观察三个阶段。
- README 草稿中已有成功、指定失败和调整耗时的方法。

### 11.6 本阶段不做

- 不做服务重启自动恢复、自动重试、消息队列和真正图片生成。

## 12. 阶段 8：前端多任务与刷新恢复

### 12.1 目标

完成任务历史页和题目要求的前端异步状态管理。

### 12.2 工作内容

- 实现 `/tasks` 历史页，按创建时间倒序展示。
- 展示模板、创建时间、状态、阶段、成功结果或失败原因。
- 仅存在 `QUEUED/PROCESSING` 时启动轮询。
- 单个任务终止后停止跟踪该任务；全部终止后停止轮询。
- 任务按 `taskId` 独立更新，不能用一个全局状态覆盖多个任务。
- 将后台 `FAILED` 与查询 `queryError` 分开。
- 查询失败时保留上次任务信息，展示“暂时无法获取最新状态”和手动刷新。
- 页面卸载、退出登录和用户变化时取消/忽略旧请求。
- 防止旧响应覆盖新状态，尤其不能让较早的 `PROCESSING` 覆盖已经返回的终态。
- 刷新后从 `/tasks` 恢复历史，并继续跟踪未完成任务。
- 成功结果支持图片预览。

### 12.3 测试

- 两个以上任务返回不同状态时互不串扰。
- 一个任务完成，不影响另一个任务继续轮询。
- 查询 500/超时不会把任务改成 `FAILED`。
- 没有未完成任务时不继续发送轮询请求。
- 用户退出或切换身份后，旧响应不能写入新用户页面。
- 刷新加载后能恢复未完成任务轮询。

### 12.4 通过标准

- 可以连续创建多个任务，并同时观察不同阶段。
- 能稳定演示一个成功任务和一个指定阶段失败任务。
- 暂时关闭后端再恢复时，前端先显示查询异常，恢复后继续得到真实任务结果。

### 12.5 本阶段不做

- 不做下载、删除、重新制作和精确百分比进度。

## 13. 阶段 9：测试与可靠性加固

## 14. 阶段 10：CI、容器与最终交付

### 14.1 目标

把项目整理成评审者可以阅读、构建、运行和复现关键场景的最终交付物。

### 14.2 CI

创建 `.github/workflows/ci.yml`：

- `push` 和 `pull_request` 触发。
- 前端执行依赖安装、lint、类型检查、测试和生产构建。
- 后端执行测试和打包。
- 缓存只用于加速，不能成为构建成功前提。

### 14.3 Docker Compose

- 一条命令启动前端、后端和 MySQL。
- MySQL 健康后再启动后端，后端健康后再认为系统可用。
- 数据库和上传目录使用命名卷。
- 验证容器内外 API 地址和 CORS/代理配置。
- 使用 `.env.example`，不提交真实密钥。
- 执行一次从无镜像、无旧数据卷的全新构建验收。

### 14.4 根 README

必须覆盖：

- 技术版本、目录结构和架构说明。
- 本地及 Compose 的构建、测试和启动命令。
- 配置、数据库初始化和演示账号。
- 主要接口、状态机和异步执行方式。
- 成功、三个指定阶段失败、耗时调整、多任务和刷新恢复的演示步骤。
- 登录与个人记录隔离方式。
- 已完成、未完成、已知限制和实际投入。
- 部署和回滚基本步骤。
- AI 工作流和第三方素材/脚手架来源。

### 14.5 最终人工验收脚本

按以下顺序完整执行并记录结果：

1. 使用全新环境启动系统。
2. 使用用户 A 登录，浏览分类和不同要求的模板。
3. 验证错误类型、超限图片和上传失败反馈。
4. 创建正常任务，确认接口快速返回且阶段逐步变化。
5. 创建多个任务，确认状态互不串扰。
6. 刷新页面，确认历史和未完成任务恢复。
7. 分别触发三个指定阶段失败，确认后续步骤停止。
8. 暂时制造查询失败，确认任务没有被错误标记失败。
9. 使用用户 B 登录，确认看不到用户 A 的素材和任务。
10. 运行全部前后端质量命令，确认 GitHub Actions 绿色。

- CI 覆盖题目要求的全部命令并通过。
- README 中的命令和演示步骤经过实际执行，不是推测。
